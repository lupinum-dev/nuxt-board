Contributions are welcome when they keep the library easier to use, test, and maintain.

## Set Up the Repo

Install dependencies from the repository root:

```bash
pnpm install
```

Start the playground or docs app:

```bash
pnpm dev:playground
pnpm dev:docs
```

The playground is the fastest place to verify interaction changes. The docs app uses the workspace packages, so examples exercise the same code consumers install.

## Run the Checks

Run the narrow check while you work, then the full set before handoff:

```bash
pnpm test:unit
pnpm typecheck
pnpm lint
pnpm format:check
pnpm test:e2e
```

Use E2E tests for browser interaction, screenshot, or docs changes. Unit tests are enough for isolated core behavior.

## Where Docs Live

Docs content lives in `packages/docs/content`.

| Folder              | Purpose                                                                                 |
| ------------------- | --------------------------------------------------------------------------------------- |
| `1.getting-started` | Install, orientation, and first board.                                                  |
| `2.essentials`      | Core concepts the reader needs before larger guides.                                    |
| `3.guides`          | Task-first guides for features such as connections, groups, serialization, and theming. |
| `4.examples`        | Live example pages.                                                                     |
| `5.cookbook`        | Focused recipes.                                                                        |
| `6.api`             | Generated and hand-written API reference.                                               |
| `7.events`          | Event and subscription reference.                                                       |
| `8.oss`             | Contribution, release, support, and security pages.                                     |

Run API generation after changing exports:

```bash
pnpm docs:api
```

## Documentation Standards

Write each page for one reader and one job. A quickstart should not become a reference page, and a reference page should not become a tutorial.

Before shipping docs, check:

- The first paragraph says what the page helps the reader do or understand.
- Examples include imports and setup when needed.
- Claims about defaults, fields, commands, and behavior match source or tests.
- Links describe the destination.
- The page ends with a useful next step.

## When Code Needs Docs

Update docs when a change affects:

- exported package APIs
- node, edge, selection, camera, or serializer behavior
- Nuxt module options or auto-imports
- default UI behavior
- migration steps for existing users
- setup commands or package names

For publishable package changes, add a changeset:

```bash
pnpm changeset
```

## Pull Request Shape

A reviewable change has a narrow scope, tests for changed behavior, and docs for user-visible changes.

Include screenshots or short recordings for visual interaction changes. For generated API docs, include the source change and the generated markdown together.
